## Q1：讲一下 poll.rs 中的队列操作

### 回答
poll.rs 里的队列是 **1024cores.net 经典算法的「侵入式无锁 MPSC 队列」**——多生产者（业务线程 `set_readiness` 入队）单消费者（poller 线程 `poll` 出队），配三个哨兵标记节点表达"空/睡眠/关闭"。

**数据结构**：
- `ReadinessNode`：节点，含 `state: AtomicState`（位打包）、三槽 `token`、`next_readiness: AtomicPtr`、`job` 回调等。
- `ReadinessQueueInner`：队列本体，含 `head_readiness`（生产者 CAS 写）、`tail_readiness`（消费者独占 `UnsafeCell`）、三个 `Box<ReadinessNode>` 标记节点、`awakener`（pipe）。

**链表方向：头插 + 尾弹**（head 生产、tail 消费）。

**五个操作**：
1. `enqueue_node`（入队）：CAS 把 head 换成新节点，新节点接旧 head 后面；返回 `prev == sleep_marker` 表示"poller 在睡，要唤醒"。
2. `dequeue_node`（出队）：跳过三标记节点；返回 `Data/Empty/Inconsistent`。`Inconsistent` = 生产者 CAS 到一半（head 已指走但 next 未接），是插入窗口期的经典竞态，消费者放弃本轮重试。
3. `clear_sleep_marker`：把睡眠态恢复成空态（CAS sleep→end）。
4. `prepare_for_sleep`：队列空时把 end 换成 sleep，返回 true（epoll 可阻塞睡）。
5. `ReadinessQueue::poll`：出队消费，CAS 消费掉就绪状态，`until` 限流，生成 `Event` 塞进 dst。

**精髓**：无锁靠"head 多生产者 CAS + tail 单消费者独占"分工；三哨兵消灭空/睡/关的边界特判；睡眠优化让高频入队只在"唤醒那一瞬"才写 pipe。

## Q2：如何评价队列设计 + 现代优雅做法 + mio 0.7 改变

### 回答
**评价**：这是 1024cores 无锁 mpsc 的标准实现（mio 0.6 抄自 `std::sync::mpsc`）。

"异常"用法的两个来源：
- **无锁算法固有（大头）**：`AtomicPtr` + CAS、`UnsafeCell` 单消费者独占、三哨兵——任何语言都这样。
- **当年 Rust 版本限制（小头）**：缺 `NonNull`（1.25）→ `*mut ()` 类型擦除；缺 `MaybeUninit`（1.36）→ `UnsafeCell` 占位初始化。

真正危险的是 `release_node` 里 `mem::transmute` 手工减 Arc 计数。

**现代优雅做法**：
1. 用 `crossbeam` / `std::sync::mpsc`，不手写 unsafe。
2. `Mutex<VecDeque> + Condvar`（99% 场景性能够）。
3. 真要手写：`NonNull` + `MaybeUninit` + `crossbeam-epoch`。

**mio 0.7 改变**（详见 Q4）：拆 `Poll`/`Registry`、删无锁队列、删 `PollOpt`、`Evented`→`Source`、`SetReadiness`→`Waker`、删 deprecated 模块。

## Q3：Poll/Registry 拆分 + 为何跟 async/await 有关

### 回答
**0.6 → 0.7 的因果链**：
```
0.6: Poll 不可 clone → 用户自己 Arc<Poll> → 只有 &Poll → register/poll 都 &self
     → poll(&self) 多线程可调 → 被迫 lock_state + Mutex + Condvar 串行化
0.7: 拆 Registry（&self + Arc/dup 共享，只管注册）+ Poll（&mut self，单线程 poll）
     → 删掉 lock_state
```
本质：被多线程共享的只是"注册入口"，不是"poll 循环"。

**为何跟 async/await 有关**：
- async/await（1.39 稳定）= 协作式并发：`async fn` → Future 状态机，`.await` 挂起/恢复。
- async 需要"挂起 + 唤醒"：future await IO → 注册 Waker → 挂起 → 就绪 → `waker.wake()` → 恢复。
- mio 0.7 引入 `Waker`（对标 `std::task::Waker`）+ 拆 `Registry`（多 worker 注册 + 单 reactor poll），正是给 async runtime 打地基。

## Q4：基于 mio-0.7.0 源码重新讲（纠正偏差）

### 回答
读源码后纠正三处记忆偏差 + 一个重大发现：

1. `Poll` 不是 `Arc<Registry>`，是**按值持有** `registry: Registry`；`Registry` 按值持有 `selector: Selector`。
2. `try_clone` 不是 Arc，是 **`dup(epfd)`**——dup 出的新 fd 和旧 fd 共享同一内核 epoll 实例。
3. **重大发现：0.7 把 `ReadinessQueue` 无锁队列整个删了**（0.6 poll.rs 2800+ 行 → 0.7 636 行含大量文档）。

**核心变化**：
- `poll(&mut self)` 就一行 `selector.select()`，无 lock_state。
- 无锁队列 + Registration 被 eventfd 的 `Waker` 取代。
- `PollOpt` 删除，`interests_to_epoll` 硬编码 `EPOLLET`（只 edge）。
- `Ready` 拆 `Interest`（注册，`NonZeroU8`）+ `Event`（返回）。
- `Evented`（&self + &Poll + opts）→ `Source`（&mut self + &Registry + interests）。
- `SelectorId` 降级为 debug 断言。
- 删 `timer`/`channel`/`deprecated` 模块。

**进化方向**：做减法——删无锁队列（eventfd 替代）、删 lock_state（&mut self 替代）、删 PollOpt（硬编码 edge 替代）、删 deprecated。

## Q5：&mut self 为何单线程 / 为何删无锁队列 / 0.7 用 async 吗

### 回答
**1. `&mut self` 是编译器编译期保证的独占**：
- Rust 核心不变式 "aliasing XOR mutability"：同一时刻要么多个 `&T`，要么唯一 `&mut T`。
- `Arc<Poll>` 只给 `&Poll`，调不了 `poll(&mut self)`（编译错误）。
- 要跨线程调 poll 必须 `Arc<Mutex<Poll>>`（运行时锁）或单线程独占。
- 所以 `&mut self` 把"多线程 poll"挡在编译期，删掉了 lock_state。

**2. 为何删无锁队列**：
- 0.6 的无锁队列服务"非 fd 事件"（Registration/SetReadiness/Timer/channel）。
- 0.7 用 eventfd（真实 fd）替代：`waker.wake()` = `write(eventfd)`，内核原子累加计数器 + epoll 就绪队列。
- 多生产者队列"下沉到内核"，用户态不用自己写无锁队列。

**3. 0.7 用 async 吗**：没有。mio 0.7 是纯同步非阻塞库，代码里无 async/await，依赖只有 log + libc。它是"给 async 打地基"，不是自己用 async。

## Q6：0.7 如何分发事件 + 怎么打磨成 async 地基

### 回答
**0.7 根本不分发事件**：`poll` 只返回 `Event`（token + readiness），用户自己 `match token`。没有 my_mio 那种"根据 token 调 job 闭包"的分发。

**timer 不在 0.7 里**：tokio 的 timer 靠"时间轮 + epoll_wait 的 timeout 参数"驱动，根本不进 epoll 树。

**async 地基三件套**：
| mio 0.7 组件 | 机制 | async 需求 |
|---|---|---|
| `Poll`（&mut） | 单线程 epoll_wait | 单 reactor 等就绪 |
| `Registry`（&self，dup） | 任意线程 register | 多 worker 注册 |
| `Waker`（eventfd） | 跨线程唤醒 | 就绪后叫醒等待方 |

tokio 的挂起+唤醒流程：worker future await IO → 存 Waker → 挂起 → reactor epoll_wait 就绪 → `waker.wake()` → future 重新入队。

**关键映射表**：tokio 用 `Slab<ScheduledIo{waker 列表}>` 维护 token→调度状态；my_mio 用 `HashMap<fd, JobEntry{闭包}>`；mio 0.7 没有表（交给上层）。

## Q7：async 有点像协程的概念

### 回答
对，而且 async/await **就是**协程——准确说是「无栈协程（stackless coroutine）」。

协程本质：能暂停、能恢复的执行单元，用户态调度（区别于线程的内核态调度）。

| | 有栈协程 | 无栈协程 |
|---|---|---|
| 独立栈 | ✅ | ❌（状态存"状态机"里） |
| 暂停点 | 任意深度 | 只能显式 `.await` |
| 代表 | Go goroutine、Lua、boost.coroutine | **Rust async**、C++20、JS async、Python asyncio |

Rust async 机制：`async fn` 编译成 Future（状态机），每个 `.await` 是状态转换点。副作用是"传染性"（async 只能被 async await）。

**串联前面的讨论**：协程的"暂停"= future 返回 Pending；"恢复"= waker.wake()；"何时恢复"的信号 = epoll/mio。所以分工是——mio 答"何时恢复"，executor 答"恢复谁、在哪个线程"，async 协程提供"怎么暂停/恢复"。

## Q8：mio 0.6 的 poll 标准玩法

### 回答
**标准玩法：单线程 event loop**（一个线程循环 poll）。lock_state 注释 "no concurrent calls to poll, which is very common" 印证。

四种玩法：
| 玩法 | 形态 | 推荐 |
|---|---|---|
| ① 单线程 event loop | 一个线程循环 poll | ✅ 标准 |
| ② one loop per thread | 每线程自己的 Poll | ✅ 多线程标准 |
| ③ 多线程共享一个 Poll | `Arc<Poll>`，lock_state 串行化 | ⚠️ 反模式（无并行收益） |
| ④ 单 poll 线程 + 多 register 线程 | register 是 &self 线程安全 | ✅ 推荐 |

`poll(&self)` 是历史包袱：它让错误的 ③ 能编译过；0.7 的 `poll(&mut self)` 是纠偏。

## Q9：mio 0.7 poll 支持哪些模式（触发模式对比）

### 回答
0.7 把触发模式从 4 种砍到 1 种——**只保留 edge-triggered**。

| 触发模式 | 0.6 | 0.7 |
|---|---|---|
| edge | ✅ | ✅（唯一，硬编码 EPOLLET） |
| level | ✅ | ❌ |
| oneshot | ✅ | ❌ |
| urgent | ✅（deprecated） | ❌ |

原因：edge 是高性能唯一选择、async 只用 edge、oneshot 可用 edge+reregister 模拟、跨平台统一、API 简化。

level 语义的替代：**draining readiness**——收到事件后反复操作直到 `WouldBlock`。

其他维度也变了：兴趣 `Ready`→`Interest`/`Event`、poll `&self`→`&mut self`、事件返回粒度更细、注册能力独立成 `Registry`。

## Q10：mio 0.7 poll 函数玩法对比（签名层面）

### 回答
三处实质变化：
1. `&self` → `&mut self`（借用）
2. 返回值 `io::Result<usize>` → `io::Result<()>`（0.6 的数量返回值已 deprecated）
3. Events 访问：0.6 有 `len()`/`get(i)`（deprecated）+ 迭代器；0.7 **只有迭代器**，删掉 `len()`/`get(i)`（因为索引访问"事件可能被插入，顺序访问不可靠"）

EINTR 处理：0.6 自动重试，0.7 不重试直接返回错误。

---

## Q11：mio 0.7 poll 标准玩法

### 回答
0.7 因 `&mut self`，玩法比 0.6 少一种（③ 多线程共享 Poll 被编译期禁止）：

| 玩法 | 0.6 | 0.7 |
|---|---|---|
| ① 单线程 event loop | ✅ | ✅ 标准 |
| ② one loop per thread | ✅ | ✅ 多线程唯一正解 |
| ③ 多线程共享 Poll | ✅（lock_state 兜底） | ❌ 编译期禁止 |
| ④ 单 poll + 多 register | ✅ | ✅（Registry 承担） |

- 标准玩法：单线程 event loop（`poll(&mut events, None)?` + `for event in &events`）。
- 多线程正解：one loop per thread（每线程一个 Poll）+ `Registry::try_clone()` 跨线程注册。
- ③ 在 0.7 里编译不过（`Arc<Poll>` 只给 `&Poll`，调不了 `&mut self`）。

**核心区别**：0.6 的 `&self` 允许错误玩法（靠 lock_state 运行时兜底）；0.7 的 `&mut self` 把"poll 必须单线程"升级为编译期强制。

## 附：今日核心结论速览

1. poll.rs 的队列是 1024cores 无锁 MPSC，头插尾弹 + 三哨兵（end/sleep/closed），无锁靠"head 多生产者 CAS + tail 单消费者"分工。
2. 无锁队列的"怪"主要是无锁算法固有，Rust 版本只贡献了 NonNull/MaybeUninit 缺失的啰嗦。
3. 0.7 删掉了整个无锁队列——用 eventfd（真实 fd）+ epoll 替代用户态模拟，"多生产者队列下沉内核"。
4. 0.7 的三板斧：`poll(&mut self)`（删 lock_state）、eventfd Waker（删无锁队列）、硬编码 edge（删 PollOpt）。
5. `&mut self` 靠编译器（aliasing XOR mutability）在编译期保证单线程 poll。
6. async/await 是无栈协程：mio 答"何时恢复"，executor 答"恢复谁"，协程提供"怎么暂停/恢复"。
7. mio 0.7 是纯同步库（无 async），是 async 生态（tokio）的地基，不是 async 实现。
8. poll 标准玩法：单线程 event loop；多线程正解 one loop per thread；多线程共享 Poll 是 0.6 反模式、0.7 已编译期禁止。
